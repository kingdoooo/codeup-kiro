# Flow 档位用预下载安装包实现钉版档位，Linux 统一钉 musl 变体

Flow 云托管执行器每次都是新机器，Kiro 官方安装脚本又只装最新版（参数只有 `--channel`，下载 URL 三处硬编码 `latest`，且
`stable/<版本>/manifest.json` 返回 403、官方不发布按版本的校验和），于是那条路上「本次跑的是哪个版本」完全不受控，
版本门每隔几天就会拒绝一次。因此 Flow 档位新增**钉版档位**：安装包由流水线的 `OSSDownload` 内置步骤从使用方自己的
**私有** OSS bucket 预先下载到工作目录，评审脚本只认一个**本地路径**、不知道 OSS 的存在，核对安装包摘要与入口文件摘要之后，
用安装包里的内层 `install.sh` 以 `KIRO_CLI_SKIP_SETUP=1` 安装。档位由 `KIRO_INSTALL_PROFILE` **显式声明**（不给缺省值），
钉版档位下安装包取不到就拒绝评审、**不回退现装**。Linux 上统一钉 **musl** 平台变体。

## Considered Options

- **放过整个 2.x（或同 minor 内的 patch）而不是逐个探测** — 拒绝，理由见 ADR-0004 的 2026-09-15 修订。
- **每次评审前跑一个 smoke test 代替探测** — 拒绝：smoke test 只验输出形状，验不了读取边界。真正的判据是完整探测
  （十二个门禁用例 + T5 正控 = 13 次真实调用、约 4 credit、顺利时 3.5–12 分钟），那是**每次升级**跑一次的量，不是每个 MR。
- **公共读 bucket + 匿名 `curl`** — 拒绝：安装包 586 MB，对象地址一旦泄露就是一次带宽账单 DoS，攻击成本极低且无法阻止。
  这个对象没有机密性，但有**成本**，所以走私有 bucket + 服务连接。
- **流水线缓存** — 拒绝：上限是「所有缓存目录打成一个 tgz 之后 ≤ 2 GB」，要和依赖缓存抢同一份预算；缓存**不能跨 job**，
  只在同一 job 的多次运行之间复用；且 15 天（文档另一处写 30 天）未更新会被自动清理。
- **Packages 通用制品仓库** — 拒绝：单个制品上限 2 GB 且计入组织制品总容量配额，更关键的是**没有 `ArtifactDownload` 内置步骤**，
  只能靠「制品源作为流水线源」或 API/curl。
- **在评审脚本里自己拉 OSS（`ossutil` 或手写 OSS V4 签名）** — 拒绝：`OSSDownload` 是官方内置步骤，鉴权走**服务连接**（RAM），
  凭证既不进 YAML 也不进流水线环境；手写签名是最容易写错、且错误表现（403）会和凭证过期、权限配错混在一起的一段代码。
- **`.tar.zst` / `.tar.xz`** — 拒绝：云托管执行器默认镜像（`alinux3` / `alinux4`）**没有预装 `zstd`**；`.tar.xz` 虽然最小（512 MB），
  但 xz 解压是单线程 CPU 密集，解出来约 1 GB。选 **`.zip`**（587 MB，`unzip` 预装，且这是官方安装脚本在 Linux 上实际使用的格式）。
- **glibc（gnu）平台变体** — 拒绝：`alinux3` 是 `PLATFORM_ID="platform:al8"`（RHEL8 / Anolis8 世系），glibc 低于 gnu 版要求的 2.34；
  已有的 `linux/x86_64:2.21.4` 探测记录显示入口文件摘要是 `940b47e5…`，即官方脚本在真实 Flow 执行器上**已经自动选了 musl**。
  musl 版是静态链接、装的时候完全不检查 glibc（内层 `install.sh` 的 glibc 分支被 `is_target_triple_gnu` 守着），
  对一台使用方控制不了的执行器，这个确定性比 3 MB 的体积差重要。
- **由集成包自动把已发布的 `KIRO_CLI_SHA256` 填进去** — 拒绝：那个变量的意义是让**使用方环境**声明它期望什么，集成包自己填等于自己出题自己判。
- **保留上一个可用版本的二进制以便回落** — 拒绝，见 Consequences。

## Consequences

- **评审脚本对 OSS 一无所知**，接口是 `KIRO_INSTALL_PROFILE` + 安装包本地路径 + 两个摘要。副作用有三个好处：本地测试不需要任何云资源
  （放一个假安装包到那个路径即可覆盖全部分支）；使用方不想用 OSS 也能用（内网制品库、自建步骤都行）；Phase 2 把 Kiro CLI 烤进
  自建执行器镜像时**同一套代码不用改**，路径指向镜像里的位置即可。
- **钉版档位下 `KIRO_CLI_SHA256` 由可选升为必填**（现装档位保持可选）。否则「下载的字节验过了，但装完之后执行的那个文件没验」，
  中间的解压 / `install -m 755` / PATH 解析是不设防的；而 libc 那一维也正是靠这个摘要覆盖（ADR-0004 2026-09-15 修订）。
- **每个进入已探测名单的元组要连带发布两个摘要**：安装包摘要（核对下载）与入口文件摘要（核对将被执行的文件）。两者不是同一个数。
  入口文件摘要与容器格式无关——安装是逐字节 `install -m 755` 拷贝，所以换压缩格式只需重发安装包摘要。
  2026-09-15 实测 2.21.4 / linux x86_64 / musl：安装包 `kirocli-x86_64-linux-musl.zip`（586 MB）
  = `bbb0a22161d5aea045919cc75e9210e61b63b8c877525f123a30610911b6c44d`，
  入口文件 = `940b47e51692c5ccb65f50a5036cb658b284bc824c2932e5b34460189c0ce4a9`。
- **档位不允许隐式判定。** 如果靠「某个来源变量是否非空」来推断档位，那么变量名拼错的表现就是静默落回现装档位装最新版，
  然后被版本门拒绝——错误信息指向 Kiro 版本，真实原因是一个拼错的变量名。这与本仓库别处一致的 fail-closed 原则相悖
  （平台键确定不了就拒、版本解析不出就拒、摘要算不出就拒）。
- **钉版档位下不回退现装。** 回退会把一次基础设施故障（桶权限变了、对象被误删）转换成一次版本门拒绝；更糟的是若最新版恰好在
  已探测名单内，回退会静默装上一个与使用方配置的 `KIRO_CLI_SHA256` 不匹配的二进制，于是同一次故障产生三种不同的错误面。
- **不做二进制级回落。** 在 Phase 2「关掉自动更新 + 探测通过才提升」之下，执行器永远不会落到未探测的版本上，所以没有可回落的场景；
  「回落」这个需求只在有东西不经同意就升级了的时候才成立，而那正是要消灭的对象。真的已经发布出去了就回退整个执行器镜像 digest。
  按版本重新下载也没有权威完整性依据（`stable/<版本>/manifest.json` 是 403），只能依赖本地保留的旧安装包，
  即 ~1.2 GB 常驻磁盘换一个不会发生的场景。
- **现装档位存在一个已知盲点**：`curl | bash` 在 glibc ≥ 2.34 的执行器上会装 gnu 变体，而平台键区分不出变体，
  于是已探测名单会判「已验证」而实际跑的是另一个二进制。该档位已被定位为不满足本仓库版本策略的降级路径，此盲点明确记录在案。
- **安装包进桶这一步必须在阿里云内部完成**（一次性）：从本机拉取实测约 230 KB/s、586 MB 要 40 分钟且会断。
  推荐阿里云 Cloud Shell（跑在云内网、预装 `ossutil`、不需要开 ECS）：`curl -C -` 续传下载 → 核对安装包摘要 → **核对通过再** `ossutil cp`。
  bucket 需与执行器同区域。
- **已探测名单里的元组有保质期。** kirodotdev/Kiro#11335 公布 2026-11-09 起 CLI 低于 1.28.2 将无法连接 Kiro 服务，
  这是**服务端**开关：版本没变、摘要没变、名单没变，但连不上了，现有门禁一个都不会响。因此需要按季度重新探测，
  并单独识别这类失败（否则现有 runbook 每一条都指向「回到已探测版本」，恰好是相反的方向）。
