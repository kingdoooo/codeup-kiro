# 行内评论只绑定它所评审的那个提交；绑不上就整轮不发（fail-closed）

Codeup 的行内评论必须带一个版本对（`from_patchset_biz_id` = 最新 MERGE_TARGET 版本、`to_patchset_biz_id` = 最新 MERGE_SOURCE 版本），行号挂在 `to` 那个版本上。而评审的输入是流水线本次 checkout 出来的提交：变更行集合、可定位判定、每条问题的 `line_number` 全部按它计算。两者不是同一个提交时，同一个行号在另一个版本里可能是完全不同的代码——一条 P0 会挂到无关的行上，读者按那个位置去看只会得出"评审员在胡说"的结论。「行号可能有偏移」这类提示补救不了挂错位置的问题：读者没有第二份信息可以对照。

因此：**to 侧的提交必须能被证明就是本次评审的那个提交，证明不了就一条行内评论都不发**，退回 `INLINE_COMMENT=0` 形态的汇总评论（按 P0→P1→P2 分组的完整问题清单）。代价是这一轮少了「问题贴在代码行上」的观感，**不丢任何问题**——完整清单里每条的说明与修复建议都在，原因也写进评论（阿里云侧的开发者看不到流水线日志）。判定放在草稿创建之前、也在拉现有行内评论之前，不写 MR（副作用的准确范围见文末 Consequences）。

## 绑不上的几种成因，处置不同

比较之前先做两件事：**锚 sha 形状**（`^[0-9a-fA-F]{7,40}$`）再 `git rev-parse --verify --quiet "<id>^{commit}"` 规范化。形状必须先锚：`rev-parse` 接受任意 revision 表达式，一个 refname、`HEAD`、`@` 都会解析成克隆里的分支顶端、恰好等于本次提交，于是「版本已证明」这条结论建立在一个从未核对过内容的取值上——这比误判成不一致严重得多（fail-open）。规范化本身是对**未观察到的形态**保守：真实 API 只观察到 40 位全 sha，缩写与大写都没见过，但字面比较一旦遇上就会把行内评论永久关掉。

| 判定 | 成因 | 处置 |
|---|---|---|
| 空、全空白、或不是 sha 形状 | 接口没返回 `commitId`，或返回了一个不是提交号的值 | fail-closed。不猜——"大概是最新那个"不构成证明 |
| 解析不出，克隆不是浅的 | 本次 checkout 之后源分支又被推送 | fail-closed。**自愈**：那次推送本身会触发新一轮评审 |
| 解析不出，克隆是浅的 | 可能是新推送，也可能是 graft 边界之下的旧提交 | 先 `fetch --unshallow` / `--deepen` 再判。加深后能解析就按下面几行走；仍是浅克隆（加深失败）⇒ **无从判定**，评论里说清这一点并建议放开克隆深度，不给任何一种自愈承诺 |
| 是本次提交的祖先 | Codeup 还没为本次推送建出版本（流水线被推送事件触发得比建版本更快） | 有界重查（见下）。命中就用新版本正常发（`patchset_biz_id` 跟着换），仍滞后则 fail-closed，评论里写「重跑流水线即可」。**不自愈** |
| 是本次提交的后代 | 新推送，且那个提交已经在克隆里（fetch 时被一起带下来） | 与"解析不出"同一处置：fail-closed，等下一轮。同一个事件不能因为对象在不在本地就给出两种结论 |
| 两个方向都不是祖先 | 源分支被 force-push / rebase 改写 | fail-closed，按新推送处置（改写本身也会触发新一轮评审） |

区分方向是必要的，因为「等下一轮」与「重跑流水线」是两条相反的建议：把滞后说成新推送，开发者会一直等一个不会到来的下一轮。

## 两次采样：把成因从推断变成证明

版本对在**两个时点**各取一次：checkout 之后、Kiro 之前一次（`INLINE_COMMENT=0` 时整个跳过，不多打接口），发布之前再一次。这样做有两个收益：

- **滞后的重查挪到评审之前**。重查只花几秒，而放在发布前意味着先烧掉一轮模型时间才发现发不出去。多数滞后在评审开始前就自愈了。
- **成因有了证据**。checkout 时一致、发布前不一致 ⇒ 评审期间确实有新推送（不必靠 git 拓扑推断）；checkout 时就不一致、重查后仍不一致 ⇒ 滞后或配置错，与推送无关。两次采样的结果都写进日志，评论里只写最终成因。

预采样判定绑不上时**不跳过 Kiro**：评审的价值在问题清单，行内只是增强。跳过会让这条 MR 本轮零评审，与 I7/I10 相悖。它只是提前把行内关掉，并省下发布前那次重复的重查。

## 滞后的有界重查

重查受两个上限约束，都在 `scripts/kiro-review.sh` 里以常量给出，**文档不复制具体数字**（复制过的那次就漂了）：

- `INLINE_LAG_MAX` —— 重查次数上限。它挡住「退避配成 0 时空转」。
- `INLINE_LAG_BUDGET` —— 总等待秒数上限。它挡住「退避累加把流水线挂住」：外层退避会累加，而 `codeup_list_patchsets` 内部本来就带自己的重试与退避，两层叠起来比看上去久得多。

退避只发生在两次尝试之间（先查再睡）：原先每轮开头先睡，第一次重查白等一个退避。

## from 侧只留痕，不 fail-closed

`from` 取「最新 MERGE_TARGET 版本」，而本地变更行集合的基准是 `merge-base(origin/<目标分支>, HEAD)`。两者对不上时**照发**，只在日志与汇总评论里留一句「行号可能有偏移」。两条实测结论支撑这个不对称：

- `line_number` 是**新文件侧**行号（spec §4.7.1 P1-02，真实 MR 上目测确认）——比较基准换了，新文件侧的行号不变；
- MERGE_TARGET 版本冻结在建 MR 时的目标顶端（= merge-base），目标分支此后前进不会生成新的目标版本（spec §4.7.1 P1-14 实测）。

所以这条分支在真实 Codeup 上几乎不触发，它实际是「P1-14 的结论失效了」的探针。正因为是探针，它的警告要**先于** to 侧的 fail-closed 落进日志：两者同时异常时先 return 会把探针一起吞掉，运维只看到「推送太频繁」。该版本没有提交号时同样打一条警告（探针本次失效），但不影响发布。

## Consequences

- 评审期间的活跃推送会让若干轮评审只有汇总评论、没有行内评论。这是有意的：宁可少一次观感，不要挂错位置的 P0。
- fail-closed 路径**不**清理上一次运行留下的孤儿草稿（清理在草稿阶段，而这条路径在那之前就返回了）。孤儿草稿只有机器人自己看得见、提交不了，无害；真正的并发安全靠流水线并发实例数 = 1（setup-guide 第 4 节第 4 步）与 Phase 2 的草稿归属标识（spec I6）。
- 「除那次 GET 之外不留副作用」只对**不滞后**的路径成立：判定为滞后时会多打几次同一个 GET 并等待退避（上限见上）；浅克隆下解析不出时还会 `fetch --unshallow`/`--deepen` 一次。这些都发生在草稿创建之前，不写 MR。
- 「绑一个与当前提交匹配的**旧** MERGE_SOURCE 版本」是更优解，但需要先探测 Codeup 是否接受非最新的 `patchset_biz_id`（记为 P1-16，可选后续）。可行的话滞后与新推送两种成因都能直接发对位置。
- 滞后重查会让这类运行多花一段等待，上限就是 `INLINE_LAG_BUDGET`（外层等待）加上 `codeup_list_patchsets` 自己的重试。只在检测到滞后时发生，正常路径零开销。
- 这条决策取代票 17 Comments 里「另开一票判方向」的说法：方向判定已在本决策内实现。
